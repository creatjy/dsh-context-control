# 能力精简、冲突与迭代分析 · 需求与执行规划

> 状态：需求草案 v0.1，等待确认后执行  
> 基线：`dsh-context-control` 0.5.26，2026-11-08  
> 关联文档：[需求与技术方案](./需求与技术方案.md) · [UI 设计](./UI设计.md)

> 2026-11-08 更新：交互模型改为按页面点击触发的 AI 建议，不再以批量 3-agent 报告为主线；UI 见 [AI建议-UI设计.md](./AI建议-UI设计.md)，接口见 [AI建议-架构方案.md](./AI建议-架构方案.md)。

## 一、背景

`dsh-context-control` 已经能回答“当前上下文被谁占用了”，也能在胶囊里逐项切换“加载 / 简介 / 隐藏”。但“能看见”不等于“知道该关什么”：

- 工具、技能、MCP、插件、系统提示段之间存在功能重叠，用户很难判断哪些是重复的；
- 某些能力看起来独立，实际存在依赖或指令冲突，关掉后可能让另一项失效；
- 会话胶囊里有几十个开关，缺少按任务类型划分的“安全关闭清单”；
- 当前只有“一键精简”这种按 token 大小的粗粒度策略，缺少证据、风险和回滚说明；
- 后续该往哪里迭代，缺少从真实能力图谱出发的路线图。

本规划要做的不是再写一个功能，而是先用独立分析得出**可验证的结论**：哪些能缩、哪些冲突、哪些适合在会话胶囊里关、下一步做什么。

## 二、目标

1. 产出一份**有证据的能力清单**：每一项能力的 token 成本、来源、用途、重叠关系、依赖关系。
2. 产出**可缩简清单**：合并、缩短、懒加载、仅简介、隐藏、暂不处理，各自给出预期收益与风险。
3. 产出**冲突矩阵**：功能重叠、指令冲突、优先级冲突、命名/权限冲突、依赖冲突，附可复现症状。
4. 产出**会话胶囊关闭建议**：按任务类型给出预设，明确“可关 / 只可简介 / 不可关”，并标注作用域与回滚方式。
5. 产出**后续迭代路线图**：按影响、成本、风险、依赖排序，形成 P0/P1/P2。
6. 分析过程本身可复查：每个结论都能追溯到 API 字段、文件路径或实测数字。

## 三、非目标

- 不自动修改全局层、项目层或 `modes.json`；
- 不删除、不卸载任何技能、MCP、插件；
- 不修改 DSH 宿主代码或宿主提示词语义；
- 不在分析阶段实现新功能；
- 不把“省 token”当作唯一目标，能力损失与任务风险必须同时标注；
- 不分析与本机 DSH profile 无关的仓库或用户数据。

## 四、分析范围与基线

### 4.1 分析对象

| 类别 | 具体对象 | 主要数据源 |
| --- | --- | --- |
| 系统提示段 | 当前 41 个 section（名称、token、来源、enabled） | `session.prompt.sections`、`modes.json` |
| 系统工具 | 当前约 147 个 tool（名称、描述、参数、token、capKey） | `session.prompt.tools`、能力目录 |
| 技能 | 已安装技能及其 `sectionNames`、简介长度 | `state.capabilities.skills` |
| MCP | 已连接服务器、工具数、token、用途 | `state.capabilities.mcp`、MCP 配置 |
| 插件 | 已安装插件、工具/页面/注入、token | `state.capabilities.plugins` |
| 运行时注入 | brief、项目规则、会话规则、压缩摘要 | `state.prompt.contexts`、`sessionRules` |
| 作用域规则 | 模式 → 全局 → 项目 → 会话的覆盖关系 | `modes.json`、`state.project` |
| 使用证据 | 当前会话/项目实际调用了哪些能力 | 会话事件、工具调用记录（只读） |

### 4.2 基线快照

执行前先取一次只读快照，作为所有分析 agent 的共同输入：

- `GET /dsh-context-control/api?sessionId=<id>`：完整 state；
- `GET /dsh-context-control/api?action=session&sessionId=<id>`：会话明细；
- `GET /dsh-context-control/api?action=check`：能力目录与工具摘要；
- `GET /dsh-context-control/api?action=diag`：能力/规则诊断；
- `modes.json`：只读副本，脱敏后使用。

快照需记录：采集时间、插件版本、会话 id、项目 id、窗口/请求/日志三种 token 口径。分析报告中的数字必须注明来自哪一次快照。

### 4.3 不在范围

- 其他机器、其他 DSH profile；
- 模型价格、订阅账单；
- 宿主内部实现的重构建议（除非直接影响插件结论）；
- 与本机无关的第三方仓库代码审查。

## 五、核心问题

分析必须回答以下问题，而不是泛泛给建议：

| ID | 问题 | 期望输出 |
| --- | --- | --- |
| Q1 | 哪些能力在功能上重复，能否合并或只保留一个入口？ | 重复组 + 建议保留项 + 预期节省 |
| Q2 | 哪些工具/段落的描述过长，可以缩短而不损失可发现性？ | 候选清单 + 改写前后 token 估算 |
| Q3 | 哪些能力当前会话根本不用，适合“简介”或“隐藏”？ | 按任务类型的关闭建议 + 风险 |
| Q4 | 哪些开关之间存在依赖，关了 A 会让 B 失效？ | 依赖边 + 最小安全集 |
| Q5 | 哪些提示段/工具/规则互相矛盾，或优先级被覆盖？ | 冲突矩阵 + 复现方法 + 解决建议 |
| Q6 | 会话胶囊应提供哪些“任务预设”，每套预设关什么、留什么？ | 预设表 + 验收任务 |
| Q7 | 下一阶段最值得做的 3–5 个迭代是什么？ | P0/P1/P2 路线图 |

## 六、判定标准

### 6.1 可缩简

对每个候选项，至少满足一项才进入“可缩简”：

- **重复**：与另一项完成同一件事，且没有独占能力；
- **低频**：当前项目/会话近 N 次调用未使用，且不属于基础工具；
- **冗长**：描述/示例占 token 比例高，但核心信息可用更短文本表达；
- **可懒加载**：只在特定任务需要，适合按需加载而不是每轮重发；
- **可简介化**：保留名称与一句话用途即可让模型知道“存在且可打开”。

每个候选项必须给出：`action`（合并 / 缩短 / 懒加载 / 仅简介 / 隐藏 / 保留）、`expectedSaving`、`risk`、`confidence`、`evidence`。

### 6.2 冲突

冲突分为六类，不能只写“有重叠”：

1. **功能冲突**：两个工具/技能做同一件事，模型可能选错；
2. **指令冲突**：两个提示段给出相反要求（例如“总是使用 X” vs “不要使用 X”）；
3. **优先级冲突**：项目/会话覆盖与预期不一致，关了但没生效；
4. **命名冲突**：capKey、工具名、section 名重复或近似，导致统计/开关错位；
5. **依赖冲突**：隐藏 A 导致 B 的工具/段落失效；
6. **口径冲突**：投影、胶囊、宿主状态栏数字不一致，导致用户不信任。

每条冲突需有：涉及来源、可复现步骤、严重级别（阻断/高/中/低）、建议解决方式、是否需要宿主改动。

### 6.3 会话胶囊中的“可关闭”

“关闭”在插件里有三种含义，分析时必须区分：

- **加载**：完整定义进入请求；
- **仅简介**：保留一句话简介，工具/正文不进入；
- **隐藏**：名称与说明都不进入请求。

会话胶囊的开关只写**会话层**，不写项目/全局；分析建议必须标注：

| 风险级别 | 含义 | 示例 |
| --- | --- | --- |
| 不可关 | 关了会破坏基本操作或当前任务 | 文件读写、shell、上下文管控自身、压缩 |
| 谨慎关 | 关了可能影响特定任务，需保留替代入口 | GitHub、AgentTeams、MCP 管理 |
| 可简介 | 保留发现能力，去掉大段定义 | 低频技能、大型 MCP |
| 可隐藏 | 当前任务完全不需要，且有明确恢复方式 | 演示技能、未使用的集成 |

建议预设（初判，待分析验证）：

- **日常编码**：保留文件/shell/搜索/Git；GitHub 与 AgentTeams 按需简介；未用 MCP 隐藏；
- **研究/写作**：保留搜索、抓取、文件；隐藏与代码执行无关的重型工具；
- **发布/运维**：保留 GitHub、shell、release 相关；隐藏演示/写作类；
- **最小上下文**：只保留当前任务显式需要的工具，适合长会话排障；
- **完整对照**：全部加载，用于回归和信任校验。

每套预设都必须给出：包含项、隐藏项、简介项、适用任务、验证任务、回滚方式。

### 6.4 迭代方向

迭代建议按“影响 × 成本 × 风险”排序，至少覆盖：

- **产品**：推荐引擎、任务预设、冲突检测、依赖图、成本估算、会话账单；
- **技术**：能力图谱、使用证据采集、投影与宿主对齐、规则生效验证；
- **体验**：一键应用预设、解释“为什么建议关”、批量撤销、变更预览；
- **工程**：单测、错误码、版本兼容、发布流程。

每条路线图需有：目标用户、解决的问题、验收标准、依赖、预估工作量（S/M/L）、风险。

## 七、工作分解

| 工作包 | 内容 | 负责 | 产出 |
| --- | --- | --- | --- |
| WP-01 | 基线快照与能力清单 | Captain | `baseline.json`、能力总表 |
| WP-02 | 冗余与 token 缩简审计 | 分析 Agent A | 可缩简清单、重复组 |
| WP-03 | 冲突与依赖审计 | 分析 Agent B | 冲突矩阵、依赖边、最小安全集 |
| WP-04 | 会话胶囊策略 | 分析 Agent C | 任务预设、风险分级、验证任务 |
| WP-05 | 迭代方向与优先级 | Captain + A/B/C | P0/P1/P2 路线图 |
| WP-06 | 汇总、去重、交付 | Captain | 主报告、执行摘要 |

### WP-01 基线快照

- 只读调用 API，保存脱敏 JSON；
- 记录采集时间、版本、会话/项目 id；
- 生成“能力总表”的初始行：名称、类型、capKey、token、来源、作用域、当前状态。

### WP-02 冗余与 token 审计

- 按功能域分组（文件、搜索、Git、团队、MCP 管理、写作、数据等）；
- 找重复工具/技能/段落，给出保留建议；
- 对长描述给出“可缩短”判断，不直接改写；
- 估算每项节省，汇总 top 20。

### WP-03 冲突与依赖审计

- 建立“能力 → 依赖”的边；
- 检查提示段之间的指令矛盾；
- 检查 capKey/工具名重复；
- 检查会话/项目/全局覆盖是否按预期生效；
- 输出可复现的冲突案例。

### WP-04 会话胶囊策略

- 定义 3–5 个任务原型；
- 为每个原型给出最小安全集；
- 标注不可关项与替代入口；
- 设计验证任务（例如“只保留最小集能否完成一次文件修改 + 搜索”）。

## 八、Agent 设计

### 8.1 角色

- **Captain（本会话）**：取基线、拆任务、汇总、裁决冲突、写最终报告；不把核心判断外包。
- **分析 Agent A（冗余/缩简）**：只看“重复、冗长、低频、可懒加载”。
- **分析 Agent B（冲突/依赖）**：只看“重叠、矛盾、优先级、依赖”。
- **分析 Agent C（胶囊/任务）**：只看“任务原型、最小安全集、风险与验证”。

### 8.2 隔离原则

- 每个 agent 使用**独立上下文**，不继承本会话的结论，避免互相锚定；
- 三个 agent 并行，拿同一份基线快照与同一套输出 schema；
- 实现方式优先用 `subagent`（独立上下文，不继承本会话）；需要持久团队时再用 agent-teams 的轻量 profile，不启动完整团队 DAG；
- 分析期间**只读**：禁止调用 `setCap`、`setRule`、`setSessionRule`、写文件、改配置；
- Agent 只能返回结构化结果，不直接改仓库；
- Captain 负责交叉验证：同一结论至少两个来源，或明确标“低置信度”。

### 8.3 输出 schema

```json
{
  "items": [
    {
      "id": "item-001",
      "type": "tool|skill|mcp|plugin|section|context",
      "name": "github",
      "capKey": "mcp:github",
      "tokens": 14425,
      "source": "session.prompt.tools",
      "usage": "current-session: 3 calls",
      "action": "brief|hide|merge|shorten|lazy|keep",
      "expectedSaving": 9000,
      "risk": "low|medium|high",
      "confidence": "A|B|C",
      "evidence": ["..."]
    }
  ],
  "conflicts": [],
  "presets": [],
  "roadmap": []
}
```

### 8.4 为什么用独立会话/子 agent

- 单会话分析会被已有结论和上下文带偏；
- 三个视角互相独立，能暴露 Captain 没注意到的问题；
- 输出 schema 固定，便于自动汇总和去重；
- 分析结果可复查：每个数字都能回到快照。

1. `00-summary.md`：一页结论（top 5 建议、top 3 冲突、推荐预设、下一步）。

4. `03-conflicts.md`：冲突矩阵与可复现案例。

如果时间有限，至少交付 `00-summary.md` + `02-simplification.md` + `03-conflicts.md` + `04-capsule-presets.md`。

## 十、验收标准

- **AC-01 覆盖**：能力总表覆盖当前 profile 的全部技能、MCP、插件、工具与系统提示段；token 最大的 80% 项目都有分析。
- **AC-02 证据**：每条“可缩简/冲突/可关”结论都有来源字段或文件路径，不能只有主观判断。
- **AC-03 可复现**：至少 3 条冲突给出可复现步骤或对照数据。
- **AC-04 可执行**：top 5 建议能在一个会话内按步骤执行，且每步有回滚方式。
- **AC-05 安全**：分析期间没有修改全局/项目配置；所有建议默认 session 作用域。
- **AC-06 风险**：每条建议标注风险与置信度；低置信度不得写成确定结论。
- **AC-07 预设可用**：至少 3 套任务预设，每套给出“保留/简介/隐藏”和验证任务。
- **AC-08 路线图**：至少 5 条迭代，含影响、成本、风险、依赖。
- **AC-09 脱敏**：报告不出现 token、密钥、完整个人路径、会话 id。
- **AC-10 可读性**：执行摘要不超过 1 页，主报告可在 15 分钟内读完。

## 十一、约束与安全

1. 分析 agent 只读；任何 `set*` 操作必须由用户明确批准后在本会话执行。
2. 默认只改会话层；项目/全局变更另开确认。
3. 不关闭上下文管控自身、文件读写、shell、压缩与当前任务必需工具。
4. 不把“当前会话没用过”直接等同于“可以全局关闭”；必须区分会话级与项目级。
5. 报告中的 token 是估算/快照值，必须注明口径与采集时间。
6. 发现密钥、token、个人路径时脱敏，不写入报告。
7. 分析本身有 token 成本，单次总预算建议 ≤ 60k tokens；超过则先交付阶段结论。

## 十二、时间与成本

| 阶段 | 内容 | 预估 |
| --- | --- | --- |
| 0 | 需求确认（本文件） | 用户确认后开始 |
| 1 | 基线快照 + 能力总表 | 10–15 分钟 |
| 2 | 三个分析 agent 并行 | 20–30 分钟 |
| 3 | 汇总、交叉验证、写报告 | 15–20 分钟 |
| 4 | 用户评审 + 可选应用会话预设 | 另计 |

分析阶段不改代码；如后续要落地“推荐引擎/预设”，另立实现任务。

## 十三、风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 能力重叠判断依赖语义，容易误判 | 建议不可靠 | 要求证据 + 置信度；Captain 交叉验证 |
| token 估算与宿主实际不一致 | 收益虚高 | 统一用宿主 `tokens` 字段；注明口径 |
| 关掉某项导致任务失败 | 体验受损 | 风险分级、最小安全集、验证任务、可回滚 |
| 分析消耗大量上下文 | 成本上升 | 限定快照与输出 schema；预算上限 |
| 三个 agent 结论互相矛盾 | 汇总困难 | Captain 裁决；保留分歧与理由 |
| 配置/报告中泄露密钥 | 安全问题 | 只读、脱敏、排除 `auth` 字段 |

## 十四、待确认问题

执行前请确认以下默认值；不回复则按默认执行：

1. **范围**：默认分析当前 profile 的全部已安装能力 + 当前会话/项目基线；是否只要当前项目？
2. **任务类型**：默认先覆盖“日常编码、研究/写作、发布/运维、最小上下文”四类；是否增加特定场景？
3. **应用方式**：默认只给建议、不改配置；是否允许分析完成后由我直接应用“会话级预设”（可随时撤销）？
4. **报告语言/位置**：默认中文，放在 `docs/analysis/`；是否需要同步更新 README 和已发布仓库？

## 十五、下一步
